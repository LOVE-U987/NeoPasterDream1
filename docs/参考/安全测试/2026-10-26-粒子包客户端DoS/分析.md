 # 粒子发射器网络包客户端拒绝服务分析

> 记录日期：2026-10-26（Asia/Shanghai）
> 代码基线：`momonyako`，HEAD `dc3ca704`
> 问题来源：三方审计报告第 1 项「恶意服务器可通过粒子包使客户端内存耗尽或长时间卡死」
> 状态：已确认，待修复
> 提交约束：修复完成并通过 audit 前，本文档不得提交

## 1. 结论

问题成立，且攻击面比审计描述更宽。`ParticleEmitterPayload`（S2C）在客户端解码时直接信任网络数据中的计数与长度字段，在读取实际字节之前就按声明值分配内存；随后的发射器 tick 也没有数量与频率上限。恶意或被攻陷的服务器只需发送很小的数据包，就能造成客户端内存耗尽、主线程长时间卡死或 tick 异常。

判定为高危：远程、无需玩家交互、只影响客户端、可稳定复现。修复不改变网络格式，不需要提升协议版本。

## 2. 基线与影响范围

- 粒子相关代码在 `momonyako` 与 `dev/0.11.x/milestone/notes` 上一致：`a4defcce..dc3ca704` 的差异未触及 `ParticleEmitterData`、`ParticleEmitter`、`ParticleEmitterHandler`。
- 触发者：恶意或被攻陷的服务器。客户端加入服务器后即可被触发，玩家不需要执行任何操作。
- 受影响：客户端进程（内存、主线程 tick、渲染）。不涉及服务端数据、存档或其他玩家。
- 不涉及：本项与 JSSE/CVE-2026-91403、Netty 依赖版本无关，属于模组自身的协议校验缺陷。

## 4. 攻击面

| 编号 | 攻击面 | 当前行为 | 后果 |
| :--- | :--- | :--- | :--- |
| A1 | `size` 超大 | `new ArrayList<>(size)` 在分配前无上限 | 5 字节 varint 可声明约 21 亿项，直接 `OutOfMemoryError` |
| A2 | `len` 超大 | 已知类型先 `new byte[len]`，未知类型直接 `skipBytes(len)` | 小包触发大数组分配；`OutOfMemoryError` 不被 `catch (Exception)` 捕获 |
| A3 | `len` 与实际字节不符 | 未校验 `len <= buf.readableBytes()` | 已知类型抛解码异常；未知类型 `skipBytes` 越界断线 |
| A4 | 粒子类型列表为空 | 全部类型未知或 `size=0` 时返回空列表 | tick 时 `randomParticle` 抛 `IllegalStateException` |
| A5 | `particlesPerTick` 超大 | 每 tick 循环 `particlesPerTick` 次 | 单包即可让客户端长时间卡死并耗尽内存 |
| A6 | `lifetime` 超大 | 仅 `age > lifetime` 时移除 | 发射器长期驻留，持续占用 CPU 与内存 |
| A7 | 活跃发射器无上限 | `ACTIVE_EMITTERS` 只增不减 | 大量普通包叠加后状态无限增长 |
| A8 | 单发射器粒子无上限 | `activeParticles` 只增不减 | 列表持续增长，内存与 tick 成本上升 |
| A9 | 维度切换不清理 | `clearAll` 只在登出调用 | 旧维度发射器残留到下一次清理 |

### 4.1 A1：计数预分配

```java
int size = buf.readVarInt();
List<ParticleOptions> list = new ArrayList<>(size);
```

`size` 来自网络，未经任何范围检查。`ArrayList` 会立即按该值分配底层数组，因此实际包体很小也能触发巨量分配。外层帧大小限制只约束真实字节数，无法消除这个问题。

### 4.2 A2/A3：长度字段

```java
int len = buf.readVarInt();
ParticleType<?> type = BuiltInRegistries.PARTICLE_TYPE.byId(id);
if (type == null) {
    buf.skipBytes(len);
    continue;
}
try {
    byte[] dataBytes = new byte[len];
    buf.readBytes(dataBytes);
    // ...
} catch (Exception e) {
    // 单个粒子解码失败不影响整体
}
```

- `len` 为负：已知类型抛 `NegativeArraySizeException` 并被吞掉；未知类型在 `skipBytes` 处抛异常。
- `len` 超过剩余字节：`skipBytes` 越界；已知类型则先分配再失败。
- `len` 极大：`new byte[len]` 抛出 `OutOfMemoryError`。它是 `Error`，不在 `catch (Exception)` 的捕获范围内，会直接向上传播。
- 未知类型走 `skipBytes`，完全绕过了长度与边界的显式校验。

### 4.3 A4：空粒子类型列表

解码循环对每个条目单独 `try/catch`，未知类型则 `continue`。因此 `size` 合法但所有条目都失败时，`decode` 仍返回空列表，`ParticleEmitterData` 构造成功。客户端 tick 时：

```java
public ParticleOptions randomParticle(Random random) {
    if (particleTypes.isEmpty()) {
        throw new IllegalStateException("ParticleEmitterData 至少需要一个粒子类型");
    }
    // ...
}
```

异常发生在客户端 tick 线程，通常导致客户端崩溃或断线。这一条不需要大包，是最低成本的中断路径。

### 4.4 A5：每 tick 粒子数

```java
for (int i = 0; i < data.particlesPerTick(); i++) {
    ParticleOptions options = data.randomParticle(RANDOM);
    Particle particle = engine.createParticle(options, position.x, position.y, position.z, 0, 0, 0);
    if (particle != null) {
        applyProcessorInit(processor, particle);
        activeParticles.add(particle);
    }
}
```

`particlesPerTick` 无上限。取 `Integer.MAX_VALUE` 时循环会执行约 21 亿次（`i == Integer.MAX_VALUE` 时条件为假而结束，不是死循环，但实际等同永久卡死），同时 `activeParticles` 持续增长直至内存耗尽。负数则直接不生成，属于合法但无意义的数据。

### 4.5 A6：生命周期

`lifetime` 只参与 `age > data.lifetime()` 判断，负值会立即移除，超大值则让发射器在约 21 亿 tick 内持续存在。`age` 自身也会在约 3.4 年后溢出，但对实际攻击没有影响。

### 4.6 A7/A8：聚合放大

单个包内所有字段都合法时，攻击者仍可高频发送大量包。`ParticleEmitterHandler.ACTIVE_EMITTERS` 没有上限，`ParticleEmitter.activeParticles` 也没有上限，最终形成与单包攻击相同的资源耗尽，只是速度更慢。

### 4.7 A9：清理时机

`clearAll()` 目前只在 `ClientPlayerNetworkEvent.LoggingOut` 调用。切换维度时旧发射器仍留在静态列表中，会继续消耗 tick 预算，直到登出。

## 5. 根因

1. 网络解码把对端声明的计数和长度当作可信值，在读取数据前按声明值分配内存。
2. 单个条目的解码失败被静默吞掉，没有把「全部条目失败」升级为整包失败。
3. `ParticleEmitterData` 构造器与 `Builder.build()` 都不校验 `lifetime`、`particlesPerTick`、`particleTypes`。
4. 客户端运行时没有发射器数量、单发射器粒子数、每 tick 总粒子的预算。
5. 清理只在登出触发。

## 6. 现有兜底为何无效

- `catch (Exception)` 只能收住单个粒子的格式错误，收不住 `OutOfMemoryError`。
- 分配发生在 `try` 之前的 `new ArrayList<>(size)`，以及 `try` 内但先于 `readBytes` 的 `new byte[len]`。
- 外层包大小限制只约束真实字节数，不约束包内声明值。
- 客户端默认信任服务端下发的视觉数据；但服务器可能恶意或被攻陷，必须按不可信输入处理。

## 7. 修复设计

### 7.1 统一安全上限

新增 `PasterDreamAPI/src/main/java/com/pasterdream/pasterdreammod/api/effect/particle/ParticleLimits.java`，集中定义上限，避免常量散落：

```java
public final class ParticleLimits {

    /** 单个发射器允许的粒子类型数上限。 */
    public static final int MAX_PARTICLE_TYPES = 32;
    /** 单个粒子选项编码后的最大字节数。 */
    public static final int MAX_PARTICLE_DATA_BYTES = 64 * 1024;

    public static final int MAX_LIFETIME_TICKS = 6000;

    public static final int MAX_PARTICLES_PER_TICK = 64;

    public static final int MAX_ACTIVE_EMITTERS = 128;
    /** 客户端每 tick 全部发射器的粒子总预算。 */
    public static final int MAX_TOTAL_PARTICLES_PER_TICK = 1024;
    /** 单发射器持有的活跃粒子上限。 */
    public static final int MAX_ACTIVE_PARTICLES_PER_EMITTER = 1024;
    /** 客户端全部发射器（含排空中的发射器）持有的活跃粒子总数上限。 */
    public static final int MAX_ACTIVE_PARTICLES = 4096;
```

取值依据：当前项目正常用法约为 `lifetime 30-100`、`particlesPerTick 3-8`、粒子类型 1-2 个，上述上限保留了足够余量，不会误伤现有特效。这些是安全上限，不是玩法数值；调整需要安全审查。

异常契约：解码层统一抛 `DecoderException`；公开构建路径（`Builder.build()`）抛 `IllegalArgumentException`；`ParticleEmitterData.fromFields` 是两者之间的唯一转换点。

### 7.2 解码层：分配前拒绝

`OptionsCodec.decode` 改为先校验再分配：

```java
int size = buf.readVarInt();
if (size < 1 || size > ParticleLimits.MAX_PARTICLE_TYPES) {
    throw new DecoderException("Invalid particle type count: " + size);
}
// 每个条目至少包含 id 与 len 两个 varint，各占 1 字节
if (size > buf.readableBytes() / 2) {
    throw new DecoderException("Particle type count exceeds remaining bytes");
}
List<ParticleOptions> list = new ArrayList<>(size);
for (int i = 0; i < size; i++) {
    int id = buf.readVarInt();
    int len = buf.readVarInt();
    if (len < 0
            || len > ParticleLimits.MAX_PARTICLE_DATA_BYTES
            || len > buf.readableBytes()) {
        throw new DecoderException("Invalid particle data length: " + len);
    }
    ParticleType<?> type = BuiltInRegistries.PARTICLE_TYPE.byId(id);
    if (type == null) {
        buf.skipBytes(len);
        continue;
    }
    try {
        byte[] dataBytes = new byte[len];
        buf.readBytes(dataBytes);
        // 原有单条解码逻辑保持不变
    } catch (Exception e) {
        // 单个粒子解码失败仍可跳过，但不再影响上限校验
    }
}
if (list.isEmpty()) {
    throw new DecoderException("Particle type list is empty");
}
return list;
```

要点：

- `size` 在 `new ArrayList` 之前校验，并额外用剩余字节数做上界。
- `len` 在 `new byte[len]` 与 `skipBytes(len)` 之前校验。
- 空列表升级为整包失败，堵住 A4。
- `DecoderException` 使用 `io.netty.handler.codec.DecoderException`，由网络层按坏包处理。
- 不变量：粒子类型段必须是 `ParticleEmitterData` 的末字段，`size` 的上界才能用当前 `readableBytes` 推断。若未来在该段之后追加字段，必须改为传入该段自身的剩余长度。

### 7.3 构造层：数据不变量

在 `ParticleEmitterData` 私有构造器中校验，`Builder.build()` 与 `fromFields` 都会经过这里：

```java
private ParticleEmitterData(Vec3 position, int lifetime, int particlesPerTick,
                            EmitterProcessor<?> processor, List<ParticleOptions> particleTypes) {
    if (position == null || !isValidPosition(position)) {
        throw new IllegalArgumentException("Invalid particle position");
    }
    if (lifetime < 0 || lifetime > ParticleLimits.MAX_LIFETIME_TICKS) {
        throw new IllegalArgumentException("Invalid lifetime: " + lifetime);
    }
    if (particlesPerTick < 0 || particlesPerTick > ParticleLimits.MAX_PARTICLES_PER_TICK) {
        throw new IllegalArgumentException("Invalid particlesPerTick: " + particlesPerTick);
    }
    if (particleTypes == null || particleTypes.isEmpty()
            || particleTypes.size() > ParticleLimits.MAX_PARTICLE_TYPES) {
        throw new IllegalArgumentException("Invalid particle type list");
    }
    this.position = position;
    this.lifetime = lifetime;
    this.particlesPerTick = particlesPerTick;
    this.processor = processor == null ? new EmptyEmitterProcessor() : processor;
    this.particleTypes = List.copyOf(particleTypes);
}
```

`fromFields` 是网络入口，把不合法的数据转换为解码失败：

```java
private static ParticleEmitterData fromFields(Vec3 position, int lifetime, int particlesPerTick,
                                              EmitterProcessor<?> processor, List<ParticleOptions> particleTypes) {
    try {
        return new ParticleEmitterData(position, lifetime, particlesPerTick, processor, particleTypes);
    } catch (IllegalArgumentException e) {
        throw new DecoderException("Invalid particle emitter data", e);
    }
}
```

`isValidPosition` 要求各分量有限且绝对值不超过 `MAX_ABSOLUTE_COORDINATE`，拒绝 `NaN`、无穷坐标与远超出世界边界的极端值，避免粒子位置异常扩散。

### 7.4 发射层：单发射器限流

`ParticleEmitter` 增加包内可见的 `tickBounded(int maxParticles)`，保留 `tick()` 作为兼容入口。生命周期结束后进入排空状态：停止生成新粒子，但继续清理并统计已有粒子，直到全部消亡：

```java
public void tick() {
    tickBounded(ParticleLimits.MAX_PARTICLES_PER_TICK);
}

int tickBounded(int maxNewParticles) {
    age++;
    EmitterProcessor<?> processor = data.processor();
    // 本 tick 是否仍处于原实现的处理器回调窗口内。
    // 到期当 tick 仍为 true，之后的排空 tick 为 false。
    boolean active = !finished;

    int attempted = 0;
    if (active) {
        processor.tickEmitter(data);

        int activeCapacity = ParticleLimits.MAX_ACTIVE_PARTICLES_PER_EMITTER - activeParticles.size();
        int limit = ParticleLimits.clampSpawnCount(data.particlesPerTick(), maxNewParticles, activeCapacity);

        ParticleEngine engine = Minecraft.getInstance().particleEngine;
        for (int i = 0; i < limit; i++) {
            attempted++;
            ParticleOptions options = data.randomParticle(RANDOM);
            Particle particle = engine.createParticle(options, position.x, position.y, position.z, 0, 0, 0);
            if (particle != null) {
                applyProcessorInit(processor, particle);
                activeParticles.add(particle);
            }
        }

        if (age > data.lifetime()) {
            this.finished = true;
        }
    }

    var iterator = activeParticles.listIterator();
    while (iterator.hasNext()) {
        Particle particle = iterator.next();
        if (!particle.isAlive()) {
            iterator.remove();
        } else if (active) {
            processor.tickParticle(particle);
        }
    }

    if (finished && activeParticles.isEmpty()) {
        this.removed = true;
    }
    return attempted;
}
```

- 生命周期结束后 `finished = true`，停止生成，但发射器继续留在 `ACTIVE_EMITTERS` 中清理并统计已有粒子；`activeParticles` 清空后才置 `removed = true`。
- `active` 在 tick 开始时快照。到期当 tick 仍为 `true`，照原实现执行一次 `tickEmitter`、生成与 `tickParticle`；之后的排空 tick 为 `false`，只移除 `!isAlive()` 的粒子，不调用 `tickEmitter` / `tickParticle`，粒子本身由 `ParticleEngine` 继续推进。因此处理器回调窗口与原实现一致。
- 因此 `MAX_ACTIVE_PARTICLES` 约束的是引擎中实际存活的发射器粒子数，而不是仅未到期发射器的跟踪量。
- `limit` 由请求值、tick 预算、存量容量与单发射器上限夹取，`for` 不可能再执行巨量次数。
- 达到单发射器粒子上限后停止创建，但仍推进生命周期与清理。
- `tickBounded(0)` 仍然推进 `age`，不会让发射器冻结占位；仍处于回调窗口时照常调用处理器。
- 返回值是尝试次数（包含 `createParticle` 返回 null 的尝试），用于保守扣减预算。

### 7.5 处理器层：全局预算

```java
public static void add(ParticleEmitterData data) {
    if (Minecraft.getInstance().level == null) {
        return;
    }
    if (!ParticleLimits.canAcceptEmitter(ACTIVE_EMITTERS.size())) {
        return;
    }
    ACTIVE_EMITTERS.add(new ParticleEmitter(data));
}

public static void tickAll() {
    if (Minecraft.getInstance().level == null || ACTIVE_EMITTERS.isEmpty()) {
        return;
    }

    int activeParticles = 0;
    for (ParticleEmitter emitter : ACTIVE_EMITTERS) {
        activeParticles += emitter.activeParticleCount();
    }
    int tickBudget = ParticleLimits.MAX_TOTAL_PARTICLES_PER_TICK;
    int activeCapacity = Math.max(ParticleLimits.MAX_ACTIVE_PARTICLES - activeParticles, 0);

    Iterator<ParticleEmitter> iterator = ACTIVE_EMITTERS.iterator();
    while (iterator.hasNext()) {
        ParticleEmitter emitter = iterator.next();
        if (emitter.isRemoved()) {
            iterator.remove();
            continue;
        }
        int allowed = Math.min(tickBudget, activeCapacity);
        int attempted = emitter.tickBounded(allowed);
        tickBudget -= attempted;
        activeCapacity -= attempted;
    }
}
```

超过发射器上限时直接丢弃新包，不淘汰已有发射器：丢弃策略更简单，也不会让攻击者通过新包挤掉正常特效。总预算用尽后，剩余发射器以 `tickBounded(0)` 推进生命周期，不会永久占位。

预算按加入顺序分配。头部发射器持续存活且需求超过总预算时，尾部发射器在其整个生命周期内得到 0，这是稳定饥饿而非暂时饥饿；威胁模型是恶意服务端，接受该降级。`activeCapacity` 按尝试数扣减，创建失败也会占用额度，属于保守估计；排空中的发射器仍计入存量，因此 `MAX_ACTIVE_PARTICLES` 对实际存量成立。

线程模型：NeoForge `PayloadRegistrar` 默认使用 `HandlerThread.MAIN`，注册的处理器会被 `MainThreadPayloadHandler` 包裹；`PDNetwork` 未调用 `executesOn(HandlerThread.NETWORK)`，因此 `ParticleEmitterHandler.add` 与 `tickAll` 都在客户端主线程执行，`ACTIVE_EMITTERS` 不存在跨线程竞态。

### 7.6 清理时机

在 `PDEffectClientEvents` 增加客户端世界卸载清理，覆盖切换维度：

```java
@SubscribeEvent
public static void onLevelUnload(LevelEvent.Unload event) {
    if (event.getLevel().isClientSide()) {
        ParticleEmitterHandler.clearAll();
    }
}
```

`PDEffectClientEvents` 已标注 `@EventBusSubscriber(modid = ..., value = Dist.CLIENT)`，只在客户端加载；`isClientSide()` 作为运行期双保险。

## 9. 兼容性

- 不改变网络字节格式，不需要提升协议版本。
- 项目内所有正常特效的取值都远低于上限，行为不变。
- 旧版本服务器若发送超出上限的数据，新客户端会拒绝该包并可能断线；这是有意的 fail-closed 行为。
- 若报文中全部粒子类型 id 在客户端未知（第三方模组粒子未安装或版本不匹配），同样整包拒绝并断开。这与 vanilla 对未知注册表项的解码约定一致；不采用 fail-soft，是因为空列表会穿过构造不变量并把非法状态带入 tick。
- `Builder.build()` 对负数与超大值改为抛异常，属于公开 API 行为变化，需要在类 Javadoc 中说明；`Builder.build()` 直接调用构造器并抛 `IllegalArgumentException`，`fromFields` 只用于网络解码并转换为 `DecoderException`。
- 发射器生命周期结束后进入排空状态，已有粒子继续渲染到自然消亡。排空 tick 不调用 `tickEmitter` / `tickParticle`，只移除已死亡粒子；到期当 tick 仍按原逻辑执行一次回调，因此处理器回调窗口与视觉结果均与原实现一致。`removed` 延迟到粒子清空，槽位占用会延长约一个原版粒子寿命。
- `ParticleLimits` 常量公开，便于其他模组适配与测试。

### 10.2 测试实现

- 上限校验与预算夹取抽成可单测的静态辅助方法，避免测试依赖客户端世界。
- 整包解码在独立测试运行器中优先通过 `Bootstrap.bootStrap()` 引导注册表；独立 JavaExec 缺少 FML 加载上下文导致标准引导失败时，回退到粒子注册表最小初始化（置位 vanilla 引导标志、触发 `BuiltInRegistries` 与 `ParticleTypes` 静态注册），再执行整包用例。两种引导都失败时，相关整包用例必须标记 `[SKIP]` 并写入 audit 报告，不得计为通过。
- 分组顺序固定为先执行校验、构造与预算用例，最后执行整包解码；引导用 `try/catch (Throwable)` 包裹，捕获 `Error`/OOM 时把整包用例标记 `[SKIP]` 并记录原因。最小初始化不触碰 `Blocks`，因此不会触发 NeoForge `FeatureFlagLoader` 对 FML 加载上下文的依赖。回退路径只保证 `PARTICLE_TYPE` 可用，测试结论仅覆盖解码与校验层；用例执行期抛出的 `Throwable` 计 `[FAIL]`，不得降级为 `[SKIP]`。
- 测试运行器使用 `[PASS]`/`[FAIL]`/`[SKIP]` 文本输出，不引入 emoji。
- JavaExec 任务设置 `maxHeapSize = '1g'`，为注册表引导留出空间；`size = Integer.MAX_VALUE` 用例只断言 `DecoderException`，不依赖小堆触发 OOM。
